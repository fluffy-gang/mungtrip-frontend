# 멍멍로드 Play 심사 최소 버전 Architecture Decision Records

## ADR-001: 심사용 버전을 별도 release 브랜치로 격리한다

### 상태

Accepted

### 맥락

현재 앱 개발은 계속 진행 중이고 작업트리에도 충돌 및 사용자 변경이 존재한다. 심사용 축소 과정에서 기능을 제거한 변경이 완성 앱 개발을 방해해서는 안 된다.

### 검토한 선택지

1. 기존 `develop`에서 심사용 기능을 직접 축소한다: 시작은 빠르지만 완성 기능을 되살리는 비용과 병합 위험이 크다.
2. 깨끗한 `origin/develop`에서 별도 release 브랜치를 만든다: 변경이 격리되며 향후 완성 앱은 동일 앱 ID로 별도 진화할 수 있다.

### 결정

전용 이슈 생성 후 `release/play-review-mvp-#<issue>` 브랜치를 별도 작업 디렉터리에 만들고, 심사용 축소 변경을 `develop`에 역병합하지 않는다.

### 이유

현재 진척을 보존하면서 심사용 버전의 안정화 범위와 변경 이력을 명확하게 유지할 수 있다.

### 결과와 Tradeoff

- 심사용 안정화와 완성 앱 개발을 병행할 수 있다.
- 두 브랜치의 앱 설정, 서명키와 versionCode 계보를 운영자가 함께 관리해야 한다.

## ADR-002: 인증 없는 읽기 전용 장소 탐색 앱으로 제출한다

### 상태

Accepted

### 맥락

계정 기능은 로그인 검토 정보, 개인정보 처리, 계정 삭제와 약관 동의 범위를 크게 늘린다. 최소 버전의 핵심 가치는 계정 없이도 제공할 수 있는 장소 정보 조회다.

### 검토한 선택지

1. 현재 인증 기반 개인화를 유지한다: 제품 방향에는 가깝지만 심사와 구현 범위가 커진다.
2. 인증을 제거하고 지도·목록·검색·상세만 제공한다: 제품 정체성을 유지하면서 완결된 최소 흐름을 만든다.

### 결정

로그인, 회원가입, 반려견 프로필과 사용자 데이터를 제거하고 익명 읽기 전용 장소 탐색만 제공한다.

### 이유

미완성 계정 기능을 숨기는 수준이 아니라 실행 경로에서 제거함으로써 심사자가 별도 자격 증명 없이 앱 전체를 검증할 수 있다.

### 결과와 Tradeoff

- 계정 삭제, 인증 실패, 필수 약관 동의와 개인화 데이터에 관한 심사 부담이 사라진다.
- 반려견 조건 기반 추천과 사용자 참여 기능은 후속 버전까지 제공하지 않는다.

## ADR-003: 네이버 지도는 유지하고 위치 권한은 제거한다

### 상태

Accepted

### 맥락

지도는 장소 간 위치 관계를 보여주는 핵심 사용자 가치지만 현재 위치는 민감 권한과 별도 데이터 고지를 요구한다. 네이버 지도 SDK는 사용자 위치 없이도 지도와 마커를 표시할 수 있다.

### 검토한 선택지

1. 목록만 제공한다: 네이티브 의존성은 줄지만 사용자가 장소 위치를 비교하기 어렵다.
2. 지도와 현재 위치를 모두 유지한다: 편리하지만 위치 권한과 개인정보 범위가 늘어난다.
3. 지도는 유지하고 현재 위치를 제거한다: 핵심 시각적 가치를 보존하면서 민감 권한을 피한다.

### 결정

제주 기본 영역 지도와 장소 마커를 유지하되 `expo-location`, 현재 위치 UI 및 Android 위치 권한을 제거한다.

### 이유

제품 방향을 분명히 보여주면서 심사용 버전의 개인정보와 권한 표면을 최소화한다.

### 결과와 Tradeoff

- 사용자는 장소 분포와 동선을 시각적으로 이해할 수 있다.
- 사용자 주변 정렬과 현 위치 이동 기능은 제공하지 않는다.
- NAVER Maps SDK라는 제3자 네이티브 의존성의 빌드 및 Data safety 감사를 계속 수행해야 한다.

## ADR-004: 식별 가능한 사용 로그를 보관하지 않는다

### 상태

Accepted

### 맥락

분석 SDK와 서버 접근 로그는 최소 버전의 가치에 필수적이지 않으며 Data safety와 개인정보처리방침 범위를 증가시킨다.

### 검토한 선택지

1. 현행 로그와 분석을 유지하고 모두 신고한다: 운영 가시성은 높지만 정책 준비 범위가 커진다.
2. 장애 대응 로그를 단기 보관한다: 절충안이지만 보관 기간과 삭제 절차가 필요하다.
3. application log에는 식별 정보를 기록하지 않고 인프라 access log는 저장 전에 비식별화한다: 운영 분석은 제한되지만 정책 범위가 가장 작다.

### 결정

분석·광고 SDK를 사용하지 않는다. 앱과 API application log에는 IP, 검색어와 기기 식별자를 기록하지 않고, 인프라 access log는 저장 전에 IP를 비식별화하고 검색 query를 제거한다. 검색어는 응답 생성 후 폐기하며 비식별 운영 지표만 보관한다.

### 이유

심사용 버전은 읽기 전용 정보 조회에 집중하므로 식별 데이터의 지속 수집 없이도 운영할 수 있다.

### 결과와 Tradeoff

- 개인정보 처리와 Data safety 선언을 최소화할 수 있다.
- 사용자 행동 분석과 개별 요청 추적 능력이 제한된다.
- 최종 선언은 AAB와 서버의 실제 동작을 감사한 뒤 확정해야 한다.

## ADR-005: API 장애는 번들 fallback 대신 운영 안정성으로 대응한다

### 상태

Accepted

### 맥락

심사 중 API 장애는 앱을 무용하게 만들 수 있지만 장소 데이터를 번들하면 중복 데이터의 동기화, 최신성 및 라이선스 관리가 추가된다.

### 검토한 선택지

1. 대표 장소를 앱에 번들한다: 첫 설치 장애를 견디지만 데이터 동기화 비용과 오래된 정보 노출 위험이 생긴다.
2. 최근 성공 응답을 캐시한다: 재방문 장애는 견디지만 심사자의 첫 설치를 보호하지 못한다.
3. 제출 직전 production API smoke test와 앱의 오류·재시도로 대응한다: 추가 운영 인프라는 없지만 심사 중 장애를 사전에 감지하지는 못한다.

### 결정

장소 데이터를 앱에 번들하거나 별도 모니터링 인프라를 추가하지 않는다. 제출 직전 카테고리·목록·검색·대표 상세 요청을 smoke test하고, 앱에서는 오류 안내와 재시도를 제공한다.

### 이유

최신 장소 데이터의 단일 소스를 유지하면서 최소한의 제출 전 확인으로 명백한 장애만 차단한다.

### 결과와 Tradeoff

- 앱과 API 사이의 데이터 불일치를 방지한다.
- API 장애 시 오류와 재시도 외의 장소 콘텐츠를 제공하지 못한다.
- 심사 중 새로 발생한 API 장애를 자동으로 감지하거나 대응하지 못한다.

## ADR-006: EAS remote versionCode와 동일 AAB 승격을 사용한다

### 상태

Accepted

### 맥락

Play Console은 이미 업로드한 versionCode를 재사용할 수 없고, 트랙마다 다른 빌드를 사용하면 검증 결과와 실제 제출물이 달라질 수 있다.

### 검토한 선택지

1. versionCode를 수동 관리한다: 단순하지만 병렬 작업과 재빌드에서 충돌하기 쉽다.
2. EAS remote auto-increment를 사용한다: 빌드마다 고유한 versionCode를 보장한다.

### 결정

EAS remote app version source와 production auto-increment를 사용한다. 내부 테스트를 통과한 동일 AAB를 비공개 테스트로 승격하고 코드 또는 설정 변경 시 새 AAB를 전체 재검증한다.

### 이유

버전 충돌을 방지하고 검증한 바이너리와 배포 바이너리의 동일성을 보장한다.

### 결과와 Tradeoff

- versionCode 계보와 아티팩트 추적이 명확해진다.
- 단순 재빌드도 versionCode를 소비하므로 build ID와 제출 이력을 기록해야 한다.

## ADR-007: 정식 앱에 릴리즈 계보와 정책 변경을 forward-port한다

### 상태

Accepted

### 맥락

심사용 기능 축소를 develop에 역병합하지 않으면 정식 앱이 필수 릴리즈 설정과 심사용 버그 수정을 잃을 수 있다. 반대로 축소 변경 전체를 합치면 정식 기능 개발을 되돌릴 위험이 있다.

### 검토한 선택지

1. 심사용 브랜치 전체를 develop에 병합한다: 릴리즈 설정은 보존되지만 기능 축소가 정식 앱에 섞인다.
2. 아무것도 병합하지 않는다: 격리는 명확하지만 앱 ID와 정책 계보가 단절될 수 있다.
3. 릴리즈 설정과 필요한 수정만 선별해 forward-port한다: 판단 기록은 필요하지만 두 목적을 함께 지킬 수 있다.

### 결정

기능 축소 변경은 역병합하지 않는다. package, 앱 이름, EAS projectId, Play App Signing, versionCode 계보, 개인정보 UI와 정식 앱에도 필요한 결함 수정만 이력과 함께 forward-port한다.

인증 또는 위치 기능을 다시 도입하는 릴리스는 배포 전에 Data safety, 개인정보처리방침, 계정 삭제와 권한 선언을 갱신한다.

### 이유

Play의 동일 앱 업데이트 계보를 유지하면서 정식 제품 개발의 기능 범위를 보존한다.

### 결과와 Tradeoff

- 심사용 축소와 정식 앱 개발의 충돌을 줄인다.
- 각 심사용 수정의 forward-port 필요 여부를 릴리즈 체크리스트에서 검토해야 한다.
